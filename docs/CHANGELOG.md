- **fix(gas): found the real "View in calendar" bug — a third code path neither `#19` nor `#20` accounted for.** Clean-room re-trace of the current source (trusting neither prior PR) found `createBookingEvent`'s `CalendarApp` fallback set `created = true`, **cleared `error` to `''`**, and never set `calendarLink`. `#20`'s banner fires on `bookingRequested && !calendarCreated`, so it stayed silent: an event genuinely existed, no link rendered, and **no warning appeared** — byte-for-byte indistinguishable from a healthy booking, reachable even with `BOOKING_CALENDAR_ID` set and the deployment current. `#20` only distinguished *created* from *not created*. `createBookingEvent` now returns a third flag, `degraded` (event exists, no link capturable), preserving the advanced-insert error that forced the fallback; `handleFormSubmission` threads a `calendarStatus` object; `sendPartnerNotification` renders an amber **"⚠ Calendar event created, but no link captured"** notice distinct from the red **"NOT created"** banner. Also fixed in the same path: a Meet booking through the fallback provisions no conference, so the partner email rendered `<a href="">Join Google Meet →</a>`, a live-looking button with an empty `href` — now a plain "No Google Meet link was created" marker. **Full resolution of the originally-observed symptom still requires one live booking** through the deployed `/exec`; the three states are now mutually exclusive and self-identifying, so that test also adjudicates `#19` vs `#20`.
- **fix(gas): em dashes cleared from every runtime string.** The audit's "4 in `buildVisitorPersonalNote` + 2 subject lines" undercounted. Actually fixed: 4 in `buildVisitorPersonalNote`, **7** subject lines (visitor no-booking, partner notification, daily digest, cold-move summary, welcome subscriber, publish notification, unsubscribe), the subscriber-email signature, the resubmission note written into the Sheet's Message column, the `'—'` empty-value placeholders in two internal emails (→ `n/a`), and one `Logger.log` string. Verified by stripping comments and grepping the remaining code: **zero em dashes outside comments.** Comments left alone (not copy).

## 2026-07-08 (later — booking privacy + calendar reliability)

- **fix(gas): PRIVACY — internal CRM data was leaking into the visitor's own calendar.** The visitor is an attendee on the real booking event, so the event description (and the `.ics` they receive) landed in their personal calendar. Both surfaces were rendering the full CRM dump (`Lead ID: AXP-…`, raw `Source`, asset class, internal `(Category)` label). Split into two helpers: **`bookingEventClientDescription(payload)`** (warm, minimal, no CRM) now feeds the Calendar **event** and the **`.ics`**; **`bookingEventInternalDescription(payload, leadId)`** (the full dump, renamed from `bookingEventDescription`) is used **only** in the internal partner-notification email. `bookingEventTitle` is now client-safe too (`AxisPoint Partners intro call with <name>`, no category label). The leadId still appears in the `.ics` `UID` (opaque machine identifier, never displayed) by design.
- **fix(gas): calendar event silently not created / "View in calendar" link missing.** Root cause of both: `createBookingEvent`'s fail-safe design (`!calId` early-return, the `Calendar.Events.insert` catch, and the upstream `handleFormSubmission` catch) only wrote to `Logger.log`, so a real config/access failure produced no event **and** an empty `calendarLink` while submission still returned success — indistinguishable from a healthy booking. `createBookingEvent` now returns `{ meetLink, calendarLink, created, error }`; `sendPartnerNotification` renders a loud "⚠ Calendar event was NOT created" warning (with the error + a pointer to `BOOKING_CALENDAR_ID` / calendar edit access) whenever a booking was requested but no event was created. **This makes the failure visible; the actual trigger is a runtime config state — verify `BOOKING_CALENDAR_ID` is set (re-run `setProperties()` in the Apps Script editor) and that the deploying account has edit access.** Not a timezone bug: slots run 8:00 AM–4:30 PM CT, so a parse offset could only shift the event's time within the day, never remove it.
- **fix(gas):** Warmed the visitor confirmation openers (meet/phone/no-booking) from the flat "We received your message. See you at the time below." to solutions-oriented copy; per-role `{{personalNote}}` personalization unchanged.
- **verify(gas):** Node harness (`vm`-loaded `Code.gs`) confirms client vs internal descriptions are genuinely different content, no CRM markers in any visitor-visible event/`.ics` line, the "View in calendar" link renders when a link is present, and the failure warning renders when it is not. Ships live only after `clasp push` + `clasp deploy -i` **and** confirming `BOOKING_CALENDAR_ID` is actually set.

- **fix(gas):** **Schema change (all lead tabs) — removed the redundant `Date Submitted` column.** `LEAD_HEADERS` drops from 31→30 columns; `Timestamp` (ISO) is now the single "when submitted" source. `sendDailyDigest` (today filter) and `moveColdLeads` (age calc + summary) read `Timestamp`, formatting to CT where a date comparison is needed. `REPORTS_ENABLED_COL` shifts 31→30. - **fix(gas + brand):** **CRM `Source` data-integrity fix.** The frontend previously wrote the visitor's "How did you hear about us?" answer (e.g. "LinkedIn") into `payload.source`, which the backend stamped into the Source column. Now `buildPayload` sends `source` as the real origin only (`'qr'` or `''`) and always sends the answer separately as `heardAbout`; the backend's new `leadSource(payload)` maps that to `QR` / blank (no `payload.page` fallback). Source now reflects only the true origin of a submission.
- **feat(gas):** **`.ics` calendar attachment on visitor booking confirmations.** `buildBookingIcs(payload, leadId, meetLink)` builds a fully-detailed `VEVENT` (America/Chicago `VTIMEZONE`, Meet-link/phone `LOCATION`, shared title/description helpers) attached to the meet + phone confirmation emails — a belt-and-suspenders backup to Google's native attendee invite. New shared helpers `bookingEventTitle` / `bookingEventDescription` keep the event and the `.ics` in sync.
- **verify(gas):** Node harness confirms all of the above (valid iCalendar for meet + phone, Source no longer leaking how-heard, partner email renders `calendarLink`). **Issue-1 finding:** the committed `sendPartnerNotification` already renders `calendarLink` correctly — the link was missing in live email because the pinned `/exec` deployment predated the #18 change, i.e. a `clasp deploy` gap, not a code bug. Ships live only after `clasp push` + `clasp deploy -i`.
